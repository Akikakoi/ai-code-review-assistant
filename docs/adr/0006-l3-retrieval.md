# 0006 · L3 检索实现：小仓库用向量检索，大仓库用符号匹配

- 状态：**部分实现**（符号匹配已落地；向量路径待办，见文末补记）
- 日期：2026-09-13
- 相关：`src/acra/context/retriever.py`、文档 §7.6

## 背景

L3 里的"相似实现"需要一个检索能力：找出仓库中同类功能的既有写法，
让模型判断这次改动是否违背了项目既有约定。

## 决策

- **仓库规模 < 5000 文件**：向量检索。索引内容为"每个方法的自然语言摘要 + 方法签名"，
  以变更方法的摘要为 query，取 top-3 且相似度 > 0.75，并过滤掉自己。
- **仓库规模 ≥ 5000 文件**：改用符号名精确匹配 + 路径相似度。

## 理由

检索本身不能成为瓶颈。大仓库上建索引与检索的开销会超过它带来的收益，
而此时"同类功能通常命名相似"这个先验足够强，精确匹配的性价比更高。

## 后果

- 命中后注入格式固定为"仓库中类似的既有实现（供参考项目约定）"，
  并在提示词里明确 **这是约定参照，不是待审代码** —— 否则模型会去评审参照代码；
- 反向引用（`get_callers`）走符号索引，O(1) 命中，不受仓库规模影响；
- 词表/嵌入模型一旦更换，`prompt_template_version` 不需要动，但需要重建索引缓存
  （缓存键含 commit sha，天然按次失效）。

## 2026-09-15 补记：先把三层线索接通，向量路径仍待办

补记的原因：这一项此前只做到"接口在、渲染在、提示词留了位置"，**没有任何东西去填**。
`callers` / `similar_impls` 恒为空列表，而空列表是**合法返回值** ——
和"确实没有调用方"长得一模一样。于是"L3 已就位"这个说法一直没被证伪过。

本轮接通了三层线索，并把两条与本 ADR 有关的偏离写在这里：

**一、向量路径未实现，且不静默退化。**
它需要 embedding 提供方，以及一次"为每个方法生成摘要"的预生成 —— 都是独立依赖。
当前**任何规模都走符号匹配**，`L3Clues.notes` 会明说
"向量检索未实现，已退化为符号名匹配（仓库 N 个文件，低于 5000 的阈值本应走向量）"。
理由与整个项目的纪律一致：`L3 跑了但没找到` 与 `L3 根本没按预期跑` 在报告上完全一样，
而处置方式相反 —— 前者可以接受，后者是缺陷。

**二、反向引用不走符号索引，改为有配额的候选扫描。**
本 ADR 原写"走符号索引、O(1) 命中"，但那个索引只对**变更文件及其引用类型**按需建立
（§7.5 的 L2 预算），不是全仓索引 —— 拿它查调用方只会稳定地返回空。
现在按路径邻近度（同目录 → 同顶层目录 → 其余）在**有配额**的文件集合上做符号名精确匹配，
并把"配额是否用尽"如实上报：用尽意味着线索可能不完整（降级），只是没找到则不是。

**三、相似实现的两个实现细节**（都会显著影响线索质量）：

- 匹配到的名字必须**有信息量**：`__init__` / `main` 这类名字对任何文件都是 1.0 匹配，
  实测变更点落在 `__init__` 时，top-3 相似实现全是各文件的 `__init__` —— 纯噪音；
- 注入前保留 0.75 阈值，与向量路径共用"只注入足够像的"语义
  （符号匹配下同名 = 1.0、同族前后缀 = 0.8）。

**四、顺手修掉一个让 L3 永远不生效的缺口。**
`l3_triggers` 算出来的触发条件此前**没有任何效果**：`level` 仍停在配置上限（默认 2），
而 L3 那一段要求 `level >= 3`。现在触发命中会把该文件升到 3，
并按实际用到的最高层级上报 `context_level_max` —— 否则 summary 里会写着"L1 + L2"
而 L3 线索其实已经注进去了。

**仍未验证**：向量路径（需要 embedding 提供方），以及历史评论在真实跨 PR 场景下的效果
（本地验证时结论库为空，走的是"查得到但为空"这条分支）。

## 2026-09-16 补记三：向量路径已实现（本地 BGE / HTTP 后端），并修正一处设计偏离

**一、嵌入文本改为确定性拼接，偏离了本 ADR 的"自然语言摘要"。**

v1 嵌入的是 **签名 + 方法源码**（截断到 1200 字符）的确定性文本，不是 LLM 预生成的摘要：

1. 摘要要按方法数计费，而索引要覆盖全仓库 —— 成本在验证阈值合理性**之前**就发生，顺序反了；
2. 确定性文本可重建、可增量（源码 content-hash 没变就不重嵌），摘要做不到；
3. bge/text-embedding-v2 都是通用文本模型，对代码的语义区分本来就有限 ——
   先验证 0.75 阈值在确定性文本上是否成立，再决定要不要上摘要。

摘要版本保留为升级路径。若后续引入，注意它会让增量缓存失效（摘要随模型/版本变化）。

**二、实现要点**（`src/acra/context/vector.py`）：

- 嵌入后端可插拔：本地 BGE（sentence-transformers，可选依赖）／HTTP 服务
  （stellar-mall rag-backend 的 `POST /embed` 形状）／OpenAI 兼容 `/embeddings`（DashScope 等）；
  按 `acra_l3_embedding_endpoint` 是否配置自动选择，**都不可用时如实说明并退回符号匹配**
- 索引落 SQLite（`<workdir>/l3-index/<repo>.sqlite`），按 (path, start_line) 主键 +
  文本 content-hash 增量；**不用 ChromaDB** —— acra 的规模是"一个仓库的方法数"，
  归一化余弦用 numpy 暴力扫描是毫秒级，引入向量数据库在这个量级换不来收益
- 默认关闭（`ACRA_L3_VECTOR_ENABLED=false`）：它需要 ~300MB 依赖 + 1.3GB 模型，
  不是"代码有了就该默认开"的东西；未启用时 L3 走符号匹配并如实说明
- BGE 向量入库前归一化，余弦退化为点积

**三、本机安装路径**（China 网络，实测）：

- torch 必须走 **CPU 专用源**：`download.pytorch.org/whl/cpu` 在本机长期停滞，
  换 `https://mirrors.aliyun.com/pytorch-wheels/cpu/`（find-links）可用
- sentence-transformers 走清华 PyPI 镜像
- 模型：`HF_ENDPOINT=https://hf-mirror.com` 下载 `BAAI/bge-large-zh-v1.5`（~1.3GB）
- 本地已有 `D:\Desktop\stellar-mall\rag-backend\data\models\bge-reranker-v2-m3`
  （2.2GB）—— 但那是 **reranker 不是 embedding**，两者不能互相替代：
  reranker 是交叉编码器，只能给"已有候选"打分，做不了全仓库召回

## 2026-09-16 补记四：真实 BGE 端到端通过，阈值初验为"合理"

依赖与模型就位后（torch 2.14.0+cpu / sentence-transformers 6.0.1 /
`BAAI/bge-large-zh-v1.5` 1.24GB，经 hf-mirror），真实模型端到端通过：

```
L3 策略：应然=vector  实然=vector
向量索引：本次嵌入 8 个方法（增量）
相似实现：
  app/order_query.py:7   0.9592   同名实现
  app/order_query.py:12  0.8886   同族实现（_with_lock）
  app/handler.py:10      0.8611   跨名字的语义命中
```

第三条是**符号匹配永远给不出的**（handler 里没有叫 find_order 的方法，
但 `Handler.get` 语义上确实依赖被改的方法）—— 这正是向量检索存在的理由。

**0.75 阈值的初验结论：合理。** 三条命中全部是真相关；同义实现 0.96、
相关调用方 0.86 都在阈值之上。但这只是 5 文件演示仓库上的单点观测，
真正的校准需要带已知相似对的多仓库语料 —— 记为待办，不据此调参。

**安装路上的两个坑（China 网络）**：

- `hf-mirror` 代理不了 HF 的新 **Xet 存储协议**（401）——必须
  `HF_HUB_DISABLE_XET=1` 走普通 HTTP；
- Xet 失败会在缓存里留下**全 0 字节的快照占位符**，第二次下载会"以为文件已存在"
  直接跳过，永远修不好 —— 要先删掉占位符再重跑（blobs 本身是完整的，秒级重建）。

## 2026-09-16 补记二：历史评论这条线索接通了，但实测**没有抑制效果**

历史评论的三段链路已全部接通并实测可见（`prior_comments_by_path` 按**结果标签**
注入 —— `[已发布]` / `[已驳回（误报）]` / `[未发布]`，pipeline 加载、builder 注入、
报告里能看到"L3 历史评论 N 条已注入"）。

然后做了它真正要回答的量测：同一个 PR 跑四遍、共用一个持久库：

| 运行 | 库里历史 | 输入 tokens | 结论 |
| --- | --- | --- | --- |
| r1 | 空 | 1771 | SQL 注入（blocker） |
| r2 | 1 条未发布 | 1883 | 同一结论 |
| r3 | 2 条未发布 | 2002 | 同一结论 |
| r4 | 3 条**已发布** | — | **仍然报出同一结论** |

（r2 的说明里看不到历史评论，是当时的实现把说明列表整个覆盖了 —— 见下。）

**结论：在这条线索的设计意图（"避免重复提出"）上，单样本观测为「没有效果」。**
模型在看到 `[已发布]` 标记的同一条 blocker 后仍然报了它。

这有两层含义：

1. **样本量与缺陷性质让这个结论不能外推** —— 只有一个用例、且那是条刺眼的
   `security/blocker`，模型选择重复它未必不合理。要下结论需要带"防重复"指标的语料。
2. **但产品层面的含义很明确**：想控制"同一问题反复骚扰作者"，**不能指望提示词**。
   确定性去重（发布前比对 path + line + 类别的已发布结论）才是可靠的层，
   提示词线索只能作为辅助。

**产品决策（2026-09-16）：确定性去重暂不做。** 接受"已报告的问题可能重复出现"，
提示词线索保留为辅助；将来重复骚扰成为实际痛点时再立项。

**顺带修掉的两个缺口**（都是这条链路接通时引入或暴露的）：

- `_load_prior_comments` 按"配置上限 ≥3"设门，而默认上限是 2 —— 触发条件在
  build() 里才把文件升到 3，于是**默认路径下历史评论永远加载不到**。已去掉该门
  （代价只是每次运行多一条 SELECT，是否注入仍由 `allow_l3` 决定）。
- builder 里先写了历史评论的说明、随后又用 `l3_notes = list(clues.notes)` 整个覆盖 ——
  **注入因此不可见**，量测时才发现。已改为 `extend`。
  这条恰好印证了那句注释存在的理由：注入必须可见，否则有没有效果无从谈起。
