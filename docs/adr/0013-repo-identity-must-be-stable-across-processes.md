# 0013 · 本地仓库身份必须跨进程稳定，否则增量审查静默失效

- 状态：已采纳
- 日期：2026-09-15
- 相关：`src/acra/store/repository.py`、`src/acra/orchestrator/pipeline.py`、`docs/adr/0010`

## 背景

实测"重复 push 的成本降幅"时，第二次运行（本该走增量）报出的文件数与变更行数
**和全量完全一样**。查库发现：一次运行对应了一行 `repository`。

根因在 `get_or_create_repository`：

```python
external_id = abs(hash(full_name)) % (10**12)   # ← 注释写的是"稳定哈希"
```

Python 的字符串 `hash()` 带**进程级随机化**（`PYTHONHASHSEED`）。
实测同一个名字在三个进程里算出三个不同值：

```
891734021780
265433778324
498243819680
```

而"本地模式跑一次审查"就是一个新进程。于是每次运行都新建一行 `repository`，
`repository_id` 每次都变 ——

> `last_reviewed_sha(session, repository_id, pr_number)` 按 `repository_id` 查，
> **永远查不到上一轮**，增量判定静默退化为全量重审。

这个缺陷的三个特征让它特别难被发现：

1. **不报错、不降级。** 它只是变贵了，而"贵"在单次运行里看不出来；
2. **没有任何日志。** 走到的是 `_prepare_diff` 里"没有历史记录 ⇒ 全量"的正常分支；
3. **单进程测试测不出来。** 同一进程内 `hash()` 是稳定的，所以断言会全绿 ——
   原来那条注释之所以写错，很可能就是因为作者只在同一个进程里验证过它。

## 决策

**一、用跨进程稳定的哈希。** `stable_external_id()` 用 `blake2b(full_name)` 取 8 字节。
它不依赖任何本地状态，因此多副本部署时同一仓库得到同一 ID。

**二、为它写一个真正跨进程的测试。** 断言方式必须是在**子进程 + 不同
`PYTHONHASHSEED`** 下取值一致。写成本进程断言等于没测 —— 这正是原来的 bug 能存活的原因。

**三、增量基线只认 `succeeded`。** `last_reviewed_sha` 的 docstring 一直写着
"上一次**成功**审查的 head_sha"，但查询没有状态过滤。同一次排查一并收紧：

| 状态 | 能否当基线 | 理由 |
| --- | --- | --- |
| `succeeded` | ✅ | 覆盖了完整 diff |
| `failed` | ❌ | 什么都没审出来，当基线等于永久跳过该段代码 |
| `queued` | ❌ | 还没跑完 |
| `degraded` | ❌ | 分析范围不完整（模型不可用 / 上下文截断 / 预算熔断） |

`last_merge_base` 用同样的过滤条件，并且必须与 `last_reviewed_sha` 取**同一次**运行：
否则"上一轮 succeeded 记了 head=H1，之后一轮 failed 记了 mb=M2"会配成 (H1, M2)，
凭空判出"rebase 了"。

## 后果与已知限制

- 收紧到 `succeeded` 的代价是：一次降级之后会重审全量。这是**用成本换正确性** ——
  拿降级运行当基线会把"那一轮没审到的部分"永久跳过，而静默漏审是最难发现的一类缺陷
  （它表现为"之后几轮都很安静"，看起来像质量变好了）。
- `mode` 字段目前是单一枚举（`full | incremental | static_only`），
  因此 `--no-llm` 的增量运行会被记成 `static_only` —— **"审了多少"与"有没有用模型"
  被压进了同一个字段**。本次不改（会影响 DB 语义与报告），但值得单独决策一次。
- 这条 ADR 与 0010 是同一类：**零件齐了、单测全绿，但合起来的那条路径从未被真实跑过。**
  区别是 0010 的缺口在语料，这里的缺口在**进程边界** —— 而进程边界正好是单测覆盖不到的地方。
