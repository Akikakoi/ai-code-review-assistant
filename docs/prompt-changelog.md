# 提示词版本与指标变化记录

规则（文档 §11.3）：每次修改提示词必须

1. 提升 `PROMPT_TEMPLATE_VERSION`（在 `src/acra/__init__.py`）；
2. 跑全量评估；
3. Precision 下降超过 2 个百分点不允许合并；
4. 把变更前后的指标记到本文件。

缓存键包含该版本号，因此提升版本号同时也是"让旧结论立即失效"的手段（§10.2）。

## v1 · 阶段二补充（未提升版本号，理由见下）

> **为什么不提升版本号**：v1 尚未发布，没有需要对照的历史基线，缓存也没有跨进程持久化，
> 因此不存在"用旧标准返回旧结论"的风险。**从 v1 正式发布之后，任何提示词改动都必须提升版本号。**
> 这条规则本身没有放宽 —— 下面两次改动都发生在首次发布之前。

### 1. 枚举取值提示做实（`system_v1.txt` 输出结构段）

实测出现过模型把"FileInputStream 未关闭"标成 `category=resource`，
结论完全正确却因为自创类别名被 Schema 整条丢弃。

处理方式是**两处一起改**，缺一不可：

- 提示词：补上常见归类（资源泄漏/空指针/条件写反 → `bug`；注入/越权 → `security`；
  死锁/竞态 → `concurrency`），明确"不要自创类别名、不要用 critical/major 这类别名"；
- 校验层：加 `normalize_enums` 同义词兜底（见 `postprocess/validator.py` 模块文档）。

**先加归一化、再改提示词**，而不是只改其一：提示词总有覆盖不到的写法，
校验层兜底才能保证"可修正的偏差不会被当作幻觉丢掉"。

### 2. `verify_v1.txt` 未改动

阶段二实现了 Verify 的执行与 verdict 处理，但提示词沿用 v1。
先跑出基线数据再决定是否调整措辞 —— 改提示词之前先量，见 `docs/adr/0009`。

### 首批评估基线（`eval/report-v1.json`，15 个缺陷注入用例）

| 指标 | 实测 | 目标（§11.2 / §16） |
| --- | --- | --- |
| Precision | **1.000** | ≥ 0.60 ✅ |
| Recall | **0.364** | ≥ 0.35 ✅ |
| Noise rate | **0.000** | ≤ 0.30 ✅ |
| Anchor validity | **1.000** | ≥ 0.98 ✅ |
| 平均评论数 | **0.27** | ≤ 6 ✅ |

Recall 只刚过线（11 个正例命中 4 个）。逐用例诊断显示漏报主要不是模型没发现，
而是候选被第 8 步置信度门槛拦下（详见下面的 Verify 对比与 `README` 的"评估暴露出的真问题"）。

### Verify 开启前后的对比（15 个用例，同一基线）

| 指标 | Verify 关闭 | Verify 开启 |
| --- | --- | --- |
| Precision | 1.000 | 1.000 |
| Recall | 0.364 | 0.364 |
| Noise rate | 0.000 | 0.000 |
| Anchor validity | 1.000（12/12） | 0.909（10/11） |
| 平均评论数 | 0.27 | 0.27 |
| 端到端耗时 | 约 5 分钟 | 约 9.5 分钟 |

**结论要如实写：在这份语料上，Verify 没有带来可测量的收益，成本却接近翻倍。**

- 两次运行的命中**集合不同**（互相替换），说明跑批间的模型随机性主导了指标波动，
  单次修复或单个开关的效果在这个样本量上测不出来；
- 基线本来就没有误报（Noise 0.000），因此"Verify 用来降噪"这个价值在这份语料上
  无从体现 —— 要验证它，需要先有带真实误报的语料；
- 唯一被证实的价值是机制层面的：5 条真阳性被 Verify 判定 `confirmed` 后**仍被门槛丢弃**，
  这是个真缺陷（已修，见 ADR 0009），但修完 Recall 未变，因为同批次里别的用例又掉了。

这也正是"不要用小样本得出'某开关有效'的结论"的实例 ——
3 个用例的子集上曾观察到 0.33 → 1.00 的召回提升，扩到 15 个用例后完全不可复现。

**因此 Verify 默认关闭**，等语料扩到上百个用例、且包含真实误报之后再决定。

## 口径变更记录（会让历史结论作废，因此单独记）

评估口径是对照文档 §11.2 校准的，期间修掉了四处**会让指标静默失真**的错误：

| 项 | 错误实现 | 正确口径 |
| --- | --- | --- |
| Noise rate | 报的是 `1 − Precision`，Precision=1 时必然"达标" | 需平台交互数据，离线标为**不可计算**；另单独报"误报率"（FP / 上报数） |
| Recall 命中 | 行号 ±2，不看类别 | 行号 ±3 **且类别同族**（正确性 / 质量 / 测试） |
| TP/FP/FN | `min(期望数, 上报数)` 估算 | 逐条匹配结果 |
| 执行失败的用例 | 不计入任何指标 | **按漏报计入**，否则失败越多 Recall 越高 |

**校准前的历史指标（含 `eval/report-v1*.json`）建立在旧口径上，不能与新口径直接比较。**
这些报告已用同一份逐用例数据在新口径下重算（`scripts/migrate_eval_report.py`），
但其中的 Recall 会因容差与类别口径变化而偏低 —— 旧数字不具参考价值。
