## 增量审查此前从未真正生效（提交 `2367f5b`，ADR 0013）

实测增量成本时发现：第二次运行的文件数/行数与全量**完全一样**。查库发现
一次运行建一行 `repository` —— 根因是
`external_id = abs(hash(full_name)) % 10**12`，而 Python 字符串 `hash()`
带 **PYTHONHASHSEED 进程随机化**（实测同一名字三个进程三个值）。
本地每次审查都是新进程 ⇒ `repository_id` 每次都变 ⇒
`last_reviewed_sha` 永远查不到基线 ⇒ **增量静默退化为全量重审**。

不报错、不降级、单进程测试全绿 —— 三个特征叠加让它活了很久。

- 改用 `blake2b` 跨进程稳定哈希（`stable_external_id`）
- 增量基线只认 `status=succeeded`；`failed/queued/degraded` 都覆盖不完整
- `last_merge_base` 与 `last_reviewed_sha` 取同一次运行，否则会凭空判出 rebase
- 测试用**真实子进程 + 不同 PYTHONHASHSEED** 断言

## 增量成本实测（脚本 `scripts/measure_incremental_cost.py`）

场景：`main ──A──B`，A 三个文件多处缺陷、B 一行小改动。
run1 full(main..A) 建基线 → run2 incremental(A..B) → run3 full(main..B) 对照。
降幅 = 1 − cost(run2)/cost(run3)（同目标状态，差别只有"有没有复用上一轮范围"）。

第一份样本（复本存 `.acra-work/incremental_cost-rep1.json`）：

| 运行 | mode | 块 | 输入 | 缓存命中 | 输出 | 成本 |
| --- | --- | --- | --- | --- | --- | --- |
| run1-full | full | 3 | 5075 | 0 | 8214 | ¥0.064509 |
| run2-incremental | incremental | 1 | 1361 | 0 | 1226 | ¥0.011439 |
| run3-full | full | 3 | 5082 | 3392 | 6647 | ¥0.045036 |

**成本降幅 74.6%、输入 token 降幅 73.2%**（目标 ≥60%）。注意 run3 占了供应商侧
提示缓存的便宜（3392 命中）而 run2 没有，因此这个降幅是**偏保守**的。

不要忽略的波动：run1 与 run3 对同一文件报出的缺陷并不相同
（run1 报"price 空检查被移除"、run3 报"SQL 注入"），与 README 记录的跑批随机性一致。
输出 token 从 1226 到 8214 波动很大，而成本主要由输出主导，所以这个比例需要复本才能定论。

### 复本结果 —— 结论是"机制成立，但这条验收标准判不了"

| 观测 | 输入 token 降幅 | 成本降幅 |
| --- | --- | --- |
| 第一次 | **73.2%** | 74.6% |
| 第二次 | **73.2%** | 57.6% |

- **输入 token 降幅两次完全相同**（确定性，只由 diff 范围决定）；
- 成本降幅差 17 个百分点，因为成本由输出 token 主导（¥6/M vs 输入 ¥3/M），
  输出在两次间 4095 → 6647 波动。
- 因此 §16 阶段三验收的"成本下降 ≥60%"**当前无法可靠判定**（两次里一次 57.6%）。
- 已把判据建议写进 README：**不要用"成本"验收它** —— 成本是输出 token 的函数，
  而输出是模型随机的部分；输入 token 才是架构决定、可复现的部分。
